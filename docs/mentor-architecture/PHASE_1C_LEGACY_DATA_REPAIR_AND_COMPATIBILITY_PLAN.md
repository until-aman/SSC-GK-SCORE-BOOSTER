# 1. Confirm the Legacy Data Interpretation

**Interpretation (locked):** the workbook represents **one logical current active plan** that was regenerated **five times**, producing **five historical task-generation batches** under a **single reused `PlanId`**.

- **One logical current active plan** = the single `MentorPlans` row with `Status='active'` (the 5th batch, `CreatedAt=2026-06-08T14:01:22.132Z`). The other 4 `MentorPlans` rows are `Status='invalid'` historical generations of the same `PlanId`.
- **Five generation batches** identified by:
  - **`CreatedAt`** — the primary signal: each `MentorPlans.CreatedAt` and its 3 `MentorTasks.CreatedAt` cluster into one batch (timestamps above).
  - **`TaskId`** — unique per task; ties a task to exactly one batch via its `CreatedAt` proximity.
  - **`SequenceNumber`** — 1/2/3 within each batch (repeats across batches → cannot identify a batch alone).
  - **`DayNumber`** — all `1` here (day never advanced); not a batch discriminator in this data.
  - **`status`** — distributes across batches (completed/snoozed); not a batch discriminator.
- **Latest generation** = batch 5 (`14:01:22.132Z`), matching the single `active` plan row.
- **Earlier-generation rows** = batches 1–4 (the 12 tasks created at the four earlier timestamps).
- **Completed evidence** = the 5 rows with `Status=completed` (+`CompletedAt`), wherever they fall across batches.
- **Snoozed backlog** = the 10 rows with `Status=snoozed`.
- **Historical-only rows** = all rows belonging to batches 1–4, plus any completed/snoozed rows not in the current generation.

**Do not** treat old-generation rows as invalid merely for being old — they are valid **historical evidence**; they are simply not **current**.

# 2. Canonical Generation-Batch Rule (compatibility concept `generationBatchId`)

Because all rows share one `PlanId`, a transitional **`generationBatchId`** is needed to separate generations. **Do not physically add this column** — it is a **read-time derived** value in the compatibility adapter.

Derivation options evaluated:
| Option | Determinism | Risk |
|---|---|---|
| MentorPlans row identity | high (5 plan rows) | task→plan link only via `CreatedAt` proximity (no FK) |
| exact `MentorPlans.CreatedAt` | high | needs tolerance window for task timestamps |
| nearest task `CreatedAt` window | medium | clustering threshold sensitivity |
| deterministic ordinal within PlanId | high | needs a stable sort key |

**Recommended (locked) deterministic method for legacy rows:**
1. Take the set of distinct `MentorPlans.CreatedAt` for the `PlanId`, sorted ascending → assign **ordinal `gen = 1..5`**.
2. For each `MentorTasks` row, assign it to the generation whose `MentorPlans.CreatedAt` is the **greatest timestamp ≤ the task's `CreatedAt`** (i.e., the plan row it was created with). Tie/within-1s clusters (batches 3–5 are seconds apart) resolve by **task `CreatedAt` ascending then `TaskId`** into the nearest plan ordinal.
3. `generationBatchId = "<PlanId>#g<gen>"` (derived string, in memory only).

The compatibility layer can then answer: which tasks belong to generation 1…5, and **which generation is current** (the one whose `MentorPlans.Status='active'` → here gen 5).

# 7. Backfill Stable Task Numbers

**Constraints:** never overwrite `SequenceNumber`; preserve it as-is; assign a new `TaskNumber`; deterministic order `(generation order, CreatedAt, TaskId)`; unique within the logical plan; completed/cancelled/historical keep their number; future tasks continue from `nextTaskNumber`.

**Two schemes evaluated:**

- **Scheme P — plan-wide 1–15 (recommended for persistence):** order all 15 rows by `(gen asc, CreatedAt asc, TaskId asc)` → `TaskNumber = 1..15`; `nextTaskNumber = max+1 = 16`.
  - *Consequence:* persisted numbers are globally unique and stable, but the **current generation's 3 tasks become 13, 14, 15** — odd as a user-facing "Task 13/14/15" on a Day-1 plan.
- **Scheme G — per-generation restart (rejected for persistence):** restart 1–3 each generation → re-introduces duplicates (the exact problem) → **rejected**.

**Recommendation (locked):** **persist Scheme P (1–15, `nextTaskNumber=16`)** for uniqueness/audit, **but decouple the user-facing number from the persisted number for the legacy transitional plan**:
- the **Today's Plan UI numbers only the current generation's visible tasks 1..k** (presentation), since earlier generations are hidden;
- the persisted `TaskNumber` (13/14/15 here) is retained for audit and never reused.
- This awkward gap is **temporary**: the next **Update My Plan** supersedes the legacy plan and the new plan starts `nextTaskNumber=1` (Phase 1A §6), so future numbering is clean (1..N).

**Backfill specifics for these 15 rows:** gen1 tasks→1,2,3; gen2→4,5,6; gen3→7,8,9; gen4→10,11,12; gen5→13,14,15. `nextTaskNumber=16` on the legacy plan row.
**`nextTaskNumber = max(backfilled TaskNumber) + 1`** for the transitional legacy plan.

(All of the above is a **plan**, not an applied write.)

# 16. One-Time Repair vs Read-Time Compatibility

**Option A — Immediate one-time Sheet repair.**
- *Advantages:* clean data; simpler repository; numbers/generations materialized.
- *Risks:* mutates live data before the new code is proven; rollback is hard (Sheets has no transaction); risk of corrupting the only active plan; founder/manual or scripted writes against a fragile positional/whitespace schema.

**Option B — Compatibility adapter first, repair later.**
- *Advantages:* **zero data mutation up front**; the adapter isolates the current generation, hides legacy contamination, and normalizes headers **on read**; the new behaviour is validated against real data via shadow reads before any write; rollback = revert code (no data to restore).
- *Risks:* adapter complexity; legacy rows linger physically (acceptable — hidden, preserved).

**Recommendation (locked): Option B — compatibility adapter first, then a verified non-destructive migration.** Safer because it never risks the single active plan, requires no founder Sheet edits, and lets us prove correctness against the real workbook before touching data. The eventual physical migration (backfill `TaskNumber`, add generation id, trim headers) runs only after the adapter + Phase 1B-style verification confirm exact behaviour, with a backup taken first.

# 18. Rollback Plan

- **Pre-migration backup:** full workbook/Sheet copy with timestamp (step 1) — the canonical restore point.
- **Old code compatibility:** keep the legacy read path available; the new adapter sits **behind a feature flag** (`MENTOR_REPO_V2`), default off.
- **Shadow reads:** run new adapter reads in parallel with legacy reads, **compare and log** (no user impact) before flipping the flag.
- **Comparison logs:** record `legacy_snapshot` vs `adapter_snapshot` task counts/ids; divergence beyond expected (15→≤3) triggers review.
- **Rollback triggers:** any of — wrong active generation selected, completed evidence missing, `StudentTopicState` mutated, snapshot shows old-gen tasks, duplicate side effects, task-action failures.
- **Restore previous behaviour:** flip `MENTOR_REPO_V2` off (instant) → legacy reads resume; if a physical write step ran, restore the step-1 backup.
- **Avoid losing new task actions during rollback:** because the adapter performs **no destructive writes** and task mutations (`complete`/`snooze`) write the same physical columns the legacy path uses, actions taken under the new adapter remain valid under the legacy path; the additive `TaskNumber`/`generationId` columns are simply ignored by legacy code.
